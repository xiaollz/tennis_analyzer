# 网球电子教练：「知识很多，却看不准自己视频的要害」— 诊断与改造方案

> 日期：2026-10-18｜对象：屈书毅｜仓库：xiaollz/tennis_analyzer（分支 `cursor/learning-1017-court-clip`，本方案只读，没有改任何文件）
> 主干：FTT（Hugh Clarke《The Fault Tolerant Forehand》+ 网站 + YouTube）｜辅助：TPA（Tom Allsopp）｜技巧补充：Bourne One Minute Tennis

## 0. 一句话结论

问题不在「知识不够」，而在三处没接上：**知识按「谁讲的、哪期视频」存放，而不是按「看到什么现象 → 可能是哪几个原因」存放**；**看视频时让模型直接下诊断，而不是只让它报可核对的事实**；**新的领悟一个接一个变成「圣经」，旧假设从没被正式证实或排除**。真人教练一眼能看出来，靠的是三样东西：脑子里有一棵按优先级排好的「症状→成因树」；同时看到球的结果和全身动作；能现场让你打一个「测试球」来排除其他可能。下面的方案就是把这三样东西做出来。

## A. 诊断：为什么「知识很多，但对着自己的视频找不到要害」

### A1. 知识按「来源」堆放，不按「症状」组织

- FTT 相关的逐视频分析，至少有两套互不相同的版本：`docs/research/ftt/video_analyses/`（46 个，按 YouTube ID 命名）和 `tennis_foundation_series/channels/fault_tolerant_tennis/raw/video_analyses/`（93 个，带时间戳）。两套里同一个视频 ID 的内容也不一样（抽查了 42BfbKsTGb4、wzLMv4ASg9s）。另外还有批量文件 `ftt/09_ftt_videos_{1,2,3}.md`、`ftt/12_ftt_videos_synthesis.md`，里面有重复（gehRK0Y6AdQ、9NirSL59an0 各出现两次）。
- 主流的 11 部分模板（例：`ftt/video_analyses/42BfbKsTGb4.md`）有「新概念、误区、口令、训练、VLM 要点」，但**没有专门的字段**写「这期解决什么症状」「它默认学员哪些环节已经没问题」，**也没有时间戳**。46 个里有 40 个正文里连 URL 或视频 ID 都没有；约 19 个的频道或教练名是模型编的，有的已被 9/24 更正过。
- 结果是：看到「肘弯、被挤住」这种现象时，没有一个入口能告诉你「FTT 里哪几期、哪几个时间点讲过这个现象，各自认为上游原因是什么」。只能凭记忆去翻零散的要点，这正是用户说的「生硬调动零散要点」。

### A2. 「症状→成因链」只有雏形，而且没接到主干上

- `docs/research/diagnostic_chains/` 只有 5 条：early_front_foot_landing、wta_takeback_midline_violation、arming_the_shot_false_lag、shoulder_flexion_instead_of_isr、tight_grip_under_pressure。
  - 来源以 Bourne 2023 为主，不是 FTT。
  - 每条只有「怎么确认」，**没有「怎么排除」**（只有 #5 有一个练习和实战差距的阈值）。
  - 没有一条覆盖用户当前的现象：引拍顶点停住、触球肘弯/偏近、小臂朝上、非持拍手早掉。
  - #3 里还开着「胸大肌主动推肘往前」，跟项目里的永久禁令冲突。
- `knowledge/extracted/ftt_video_diagnostic_chains.json` 有 18 条链（含 check_sequence），但**没有引用任何来源视频**，中英文混杂。
- `evaluation/diagnosis_engine.py` 里只有 chain #1 真的接进了代码。它的层级（L1–L5）和 chain 文档的层级（L1–L10）对不上。
- `FOREHAND_COMPLETE_TAXONOMY.md` 每层列了「失败模式」和「覆盖视频 ID」，但两边**没有互相连起来**。`DRILL_INDEX.md` 是「症状→练习」，跳过了「成因」这一步。

→ 缺的是一个能用的**鉴别诊断**结构：同一个现象，列出几个可能的上游原因，并给出区分它们的测试。

### A3. 缺少「从可观测事实到成因」的检索入口

现有入口都是从概念出发的：HSA、ESR、F1–F7、VLM Q1–Q52（`knowledge/templates/vlm/system_prompt.md.j2`）。很多问题本身就嵌着项目理论和 PASS/FAIL 标签，比如「胸部陷阱」「火车轨道」「ESR 是否早启动」。这等于把答案写进了问题，和 10/17 发现的「提示词引导」是同一个病（`docs/record/learning.md:12140`）。`evaluation/vlm_analyzer.py` 还会自动注入用户画像（`knowledge/extracted/user_journey/user_profile.json`），**设计上就不中立**。

### A4. 让视频模型做了它做不可靠的事

`docs/research/user_clips/` 里 10/17 那段视频的 10 份结果说明了模型能做什么、不能做什么：

| 类别 | 10/17 实测 | 结论 |
|---|---|---|
| 拍数和时间点 | 5 拍（2.5-flash 数成 7） | 新模型稳定 |
| 触球时肘明显弯 | 所有运行一致 | 粗粒度事实，稳定 |
| 引拍顶点有停顿 | 一致 | 稳定 |
| 几乎没有步法/分步 | 一致 | 稳定 |
| 肘离身体近还是远 | argon 和 flash 相反 | 侧后方机位看不准深度 |
| 触球后重心向前还是向后/向上 | 三份三种答案 | 不稳定 |
| lag 拍头指向（F1） | 同一模型两次答案不同 | 不稳定 |
| 击球早还是晚（F6） | flash 两次：早 / 晚 | 不稳定 |
| 小臂朝上还是水平 | 4 份问卷说「水平」，整体分析说「朝上」 | 不稳定，而且受问法影响 |

另外：**提示词原文没有保存**（learning.md:12140 说存在 user_clips/，实际不在），所以以后无法复现。仓库里也没有「本地视频 inline 发 Gemini」的脚本，10/17 走的是外部路线。

**结论**：模型能稳定给出「数得出来、看得见有没有」的粗事实；凡是涉及**角度、深度、先后顺序、重心、力和放松**的判断，单机位手机视频下都不可靠。这些必须靠固定机位 + Pose/抽帧，或者用户本人的体感和球的结果来补。

### A5. 训练记录里「假设」很多，「结案」很少

- 4/27 到 10/17 大约有 15–18 次「圣经 / 根因 / 核心」级的宣告，平均每 10 天一次（例：4/27 右脚轴、5/3 HSA、5/8 ESR、5/13 几何、9/20 藏肘亮肩、9/23 髋命门、10/14 次序钉死、10/15 放松是触发点）。
- 旧观点换个名字又回来，但没有互相链接：10/14「右肩放松」≈ 5/11「右手臂彻底放松」；10/15「手腕紧」≈ 3/15 第 411 行；10/17「被挤住」≈ 4/26「击球点」。
- 几乎每条都以「待球场/录像验证」结尾，但**后面没有一条回来写验证结果**。
- 10/17 的时间轴和索引标题还挂着被提示词带偏的那次结论（learning.md:232、303）。
- 统一框架的权威排序把 USER 放第一（`docs/research/_synthesis/UNIFIED_FOREHAND_KNOWLEDGE_FRAMEWORK.md` §2），而 CLAUDE.md 规定「与权威冲突时以权威为准」。两处规则自相矛盾。

→ 缺一份**问题登记表**：每个假设都有状态（待验证 / 证实 / 排除 / 合并到某条），新的领悟只能更新这张表，不能另立「圣经」。

### A6. 缺少「必须纠正 vs 个人风格」这道过滤

FTT 书里明确写了：爆发式正手中，**髋转是 fundamental，肘弯曲程度是 discretionary**（`docs/research/ftt/01_ftt_book.md:720`）。而 10/17 各模型最一致的事实恰好是「肘明显弯」。如果没有这道过滤，我们会花力气去追一个 FTT 认为可以是风格的东西。真人教练首先做的就是这一步：先分清哪些必须改，哪些不用管。

### A7. 没有记录「球的结果」

FTT 的整套逻辑从结果出发：容错、落点、高度、旋转。而我们给模型的只有侧后方 19 秒的身体动作，**球落在哪、下网还是出界、是否被挤住的手感**，一概没记。真人教练是同时看球和人的。缺了这一项，任何诊断都没有锚点。

## B. 把知识库重组成「诊断用」的形态（FTT 主干）

### B1. 目录结构（建议新建 `docs/diagnosis/`，旧文件原地保留，只做链接）

```
docs/diagnosis/
├── README.md                    # 怎么用；权威顺序：FTT 主干 > TPA 辅 > Bourne 技巧；与其它体系冲突时的裁决规则
├── 00_principles.md             # FTT 诊断原则：网球基本定理、容错、主动 vs 被动、必须纠正 vs 风格、结果优先
├── tree.md                      # 一棵诊断树（mermaid），按 FTT 阶段排：准备/Unit Turn → 放置 → 前挥/髋 → 触球 → 随挥
├── observables/                 # 可观测事实目录（OBS-xx），每条写清：哪个机位、哪一帧、谁来测、可靠度
│   └── OBS-01_contact_elbow_bend.md …
├── symptoms/                    # 用户能报出的结果和体感症状（SYM-xx）：下网、出界、球软、被挤住感、手腕酸…
├── faults/                      # 动作层面的「故障」（FLT-xx），诊断主条目，统一模板见 B2
├── drills/                      # 练习（DRL-xx），只放发球机低速 / mini tennis / 影子挥拍能做的
├── sources/                     # 来源卡：一期视频/一篇文章/一章书一张卡（SRC-FTT-<ID>、SRC-TPA-<ID>、SRC-BRN-<章>）
├── index/
│   ├── obs_to_fault.md          # 反向索引：看到某个事实 → 候选故障（诊断入口）
│   ├── symptom_to_fault.md      # 体感/结果症状 → 候选故障
│   └── source_to_fault.md       # 每期视频挂在哪些故障上
└── user_case/
    ├── problem_register.md      # 用户的问题登记表：每个假设一行，状态 + 证据链接
    └── sessions/2026-10-xx.md   # 每次视频诊断的报告（按 C 的输出模板）
```

要点：
- **通用知识**（faults / sources）和**用户个人情况**（user_case）分开放。现在很多视频分析把两者混在一起，比如「对接 11 字口令」「4/27 圣经」，导致知识没法复用。
- 一个故障只有一张卡；多个教练的说法都作为证据挂到这张卡上，而不是每个教练一套。

### B2. 故障卡（FLT）统一模板

| OBS | 机位 | 帧 | 测量方式 | 可靠度 |

| OBS-03 触球时手到躯干的距离 | 正后方 | 触球帧 | Pose 抽帧 | 中 |

## C. 视频诊断流水线（固定下来）

### C1. 固定什么

- **模型**：只用 **gemini-3.8-flash**（learning.md:12144 已定为 skill 默认）作为**事实抽取器**，固定版本号和提示词版本号，每次输出文件头记录 `model / prompt_version / run_id / 温度`。不再拿 argon 等其他模型来「投票」，它们之间的矛盾只会增加噪音。一致性靠**同一模型重复 3 次 + Pose 核对**来保证。中转是否允许设温度为 0：**不确定**，需在第一次运行时确认。
- **模型的角色**：只报事实，不诊断。诊断由我们这边按诊断树做，模型看不到任何项目概念。

### C2. 拍摄规范（用户补拍）

| 机位 | 位置 | 主要看什么 | 优先级 |
|---|---|---|---|
| **S 正侧面 90°** | 站在用户正面朝向的一侧（面对用户胸前），垂直于出球方向，距离 3–4 m，镜头约腰高 | 触球点在前髋之前多少、肘角、躯干倾斜、引拍顶点停顿时长、早晚 | **必须** |
| **B 正后方** | 用户身后，沿出球方向，约 4–5 m，略高于头 | 手到躯干的距离（被挤住）、挥拍路径向外还是横扫、Unit Turn 幅度、**球的落点** | 强烈建议 |
| 现有侧后方 | — | 只作参考，不再作为主机位 | 可停用 |

- 横屏，1080p，**60 fps 以上**（手机能 120 更好），三脚架固定，**全身 + 球拍 + 身前约 2 m 空间都在画面里**，光线充足。
- 每段 8–10 球。开拍时口播「第 X 组」并拍一下手作为音频对齐点。只有一部手机就两组换一个机位。
- **结果记录**：每球打完用一个词口播结果，例如「好 / 网 / 长 / 偏 / 挤」，手机会录进音轨。这是诊断的锚点（见 A7）。
- 拍摄当天的训练协议，开头固定提醒：**准备时鼻吸，启动前挥至触球时用嘴短促呼气。**（呼气只做节奏锚和张力阀门，不是发力来源；不屏气。若伴随前额/枕部痛、眩晕、恶心，当天停止挥拍并就医评估。）

### C3. 流水线五步

**第 0 步 预处理（脚本需求，不写代码）**
- 旋转纠正（`core/video_processor.py` 已有）。
- 用音频 + 手腕速度定位每一拍的触球（`evaluation/event_detector.py` 的 HybridImpactDetector）。
- 每拍切成独立片段，并导出关键帧拼图：Unit Turn 完成、引拍顶点、下落、触球前 3 帧到后 3 帧、随挥结束。
- 跑 Pose，存每拍的关键数据。

**第 1 步 事实抽取（三层事实，分别由不同手段负责）**

| 层 | 内容 | 谁负责 | 规则 |
|---|---|---|---|
| A 层：模型稳定 | 拍数和时间点；有无引拍停顿；有无分步/调整步；站位类型（开放/半开放/关闭）；触球时肘「明显弯 / 接近直」；非持拍手是否在触球前就已落下；球大致飞向 | gemini-3.8-flash，3 次 | 3 次一致才采纳 |
| B 层：需机位 + Pose/抽帧 | 触球肘角（S）；触球点相对前髋（S）；手到躯干距离（B）；躯干倾角变化（S）；引拍顶点停顿时长（时间序列）；手腕路径高低（S）；髋肩转动先后（B，2D 只能粗估） | Pose + 关键帧人工核对；模型只作参考 | 以测量为准；模型与 Pose 冲突时记「待核」并出图 |
| C 层：单机位手机视频不可观测，**不问模型** | 前臂旋内/ISR、lag 的真实程度、肌肉是否在用力、握拍力度、是否放松、脚底重心分布、触球瞬间拍面角度 | 用户体感报告 + 确认/排除测试 | 只能来自体感和测试，不能来自视频 |

**防止提示词引导的五条硬规定**：
1. 提示词里不能出现任何项目术语、用户的假设或教练视频内容。只交代「一位业余球员对着低速发球机打正手」。
2. 全部用**逐拍、选择题 + 「看不清」选项**，并要求给出证据的时间点（秒）。
3. 不问「有没有某某问题」，只问「是 A 还是 B 还是看不清」，选项顺序每次随机。
4. 提示词放在一个版本化文件里，每次输出记录版本号；**改提示词 = 升版本号**，旧结果不能和新结果混着比。
5. 事实抽取和诊断分两步，中间不回传。不允许出现「先给模型看帧图提示、再让它修正」的二轮（10/7 已发现这样不能算独立验证，learning.md:11976）。

**第 2 步 事实对账（处理矛盾）**
- 同一模型 3 次：3/3 一致 → 采纳；2/3 → 「弱」，需 Pose 或抽帧佐证；其余 → 「未知」。
- 模型与 Pose 冲突：以 Pose 为准，但要看 Pose 的置信度。Pose 低置信 → 出关键帧图让用户或我们人工看一眼。
- **跨拍一致性**：习惯性故障应在 5 拍中至少出现 4 拍。只出现 1–2 拍的记为「偶发」，不进根因。
- 永远不用「第二个模型」来决胜负。不确定就写不确定。
- 输出一张「事实表」：每条事实带 OBS 编号、来源（模型/Pose/人工）、一致率、证据帧。

**第 3 步 匹配诊断树（我们这边做）**
1. 先过 `00_principles.md`：结果锚点（球去哪了、口播结果）→ 剔除「风格项」（如单独的肘弯）。
2. 用 `index/obs_to_fault.md` 和 `symptom_to_fault.md` 把事实映射到候选故障。
3. 每个候选沿成因链往上游追，**按 FTT 阶段顺序，越靠前的越优先**（准备 > 前挥 > 触球 > 随挥），这和真人教练「先修上游」一致。
4. 打分：A/B 层证据数 × 跨拍一致性 × 与结果症状的吻合 × 与问题登记表历史的吻合（只作加减分，不能单独定罪）。
5. 每个候选写出：什么证据会推翻它。

**第 4 步 输出（固定模板）**

```
最可能的根因（最多 3 条，排好序）
  1. FLT-xx 名称｜置信度：高/中/低
     证据：OBS-xx（来源，一致率，帧号）…；结果锚点：…
     推翻条件：若 …… 则排除
     FTT 依据：SRC-FTT-<ID> mm:ss（未核对的标出）
  2. …
已排除 / 不处理（风格项）：…
无法从本次视频判断：…（需要哪个机位或哪个测试）
下一次只改一件事：
  - 外部目标（一句话，Intuition-First）
  - 发球机低速 30–50 球：分组（如 10 基线 + 3×10 改动 + 10 复测），每组口播结果
  - 验证标准：哪个 OBS 应该往哪个方向变，变多少算成立
  - 开头固定呼吸提醒
```

- 首次交付给用户时，按 CLAUDE.md 写成**一整段自然段**（包含整体表现、1–2 个主问题和证据、事实/推论/不可观察的区分、FTT 视频和时间点、下次训练主线）。上面的结构化模板作为附件存进 `user_case/sessions/`。

**第 5 步 结案**
- 下一次视频跑完，回到问题登记表：目标 OBS 按预期变化 → 「证实」；没变或变反 → 「排除」或改排下一候选。这一步是现在完全缺失的闭环（A5）。

### C4. 用 10/17 那段视频演示一遍（说明新流程会得出什么）

- A 层可采纳：5 拍、肘明显弯、引拍顶点停顿、几乎无步法。
- 过滤：「肘弯」单独属风格项（书 :720），不直接定罪。
- 候选：「顶点停顿 + 无调整步 + 疑似偏近」→ FLT-01（站位）、FLT-03（停顿重启）、FLT-02（手找球）。三者都缺 B 层证据（没有正侧面和正后方机位）。
- 「小臂朝上还是水平」属 B 层，本视频判不了，不应据此建立理论。
- 输出应该是：「置信度低；下次补 S + B 机位；先做 FLT-01 的确认/排除测试：站远半步打 10 球，看『挤』的口播次数是否明显减少」。这比当天得出「手主导 + 触球区僵」的结论更诚实，也更省球。

## D. 面对新的教练视频：如何拆成「具体问题」并挂到同一棵树上

### D1. 来源卡（SRC）统一模板，每期视频入库必填

```markdown
# SRC-FTT-<YouTubeID>  标题（核对过的原标题）
- URL｜频道（核对）｜教练｜时长｜发布日期｜入库日期｜抽取模型+提示词版本｜时间戳核对状态
## 1. 解决的症状（这期的「主诉」）：SYM-xx / FLT-xx（可多个，标主次）
## 2. 它认为的上游成因（教练自己的因果链）：A → B → 症状；对应 FLT 编号；是否与现有树一致
## 3. 默认前提（最容易漏）：针对哪类球员（级别、握拍、单/双反无关等）；默认哪些环节已经没问题；适用的来球情况
## 4. 处方：练习（能否在发球机低速 / mini tennis / 影子挥拍里做）；感受提示（原话）；验证方式
## 5. 主张清单（每条一行）：主张｜时间戳｜挂接的 FLT/OBS｜类型（症状描述 / 成因 / 练习 / 感受 / 观测标准）
## 6. 层级判断：这期是「根因层」还是「症状层的补丁」？
## 7. 与 FTT 主干的关系：一致 / 细化 / 冲突（冲突写清楚，裁决按 README）
## 8. 用户关联：只放 problem_register 的链接，不在这里写个人结论
```

### D2. 抽取规则

- **抽取时不告诉模型用户的问题**（同样是提示词引导的风险）。先得到中立的「这期讲了什么」，再由我们单独做「对用户意味着什么」。
- YouTube 视频可用现有的 `scripts/youtube_gemini_analyze.py` 路线，但要换成上面的结构化提示词，并要求每条主张给时间戳。
- 时间戳要抽检：每批至少抽 10% 回到视频核对，核对后标「已核对」。

### D3. 挂树规则（避免孤立存放）

每条主张只能落到下面四种去处之一：
1. 给已有 FLT **加证据**（最常见）；
2. 给已有 FLT **加一条上游成因边**（需写清楚教练的推理，单源标「单源」）；
3. 给已有 FLT **加一个练习或感受提示**；
4. 提议**新 FLT**：需要 FTT 有出处，或 TPA/Bourne 等两个以上来源一致，否则先放「待定区」。

**新视频不能产生「圣经」**，最多只能把问题登记表里某一条的状态往前推。

**前提核对**：处方挂到用户身上之前，先查第 3 节「默认前提」是否满足。例如一期视频默认「Unit Turn 已经到位」，而用户 FLT-04 还开着，就先不采纳这期的处方。

### D4. 「认准一个教练看透」的落实

同意用户的判断。建议的 FTT 阅读顺序：**书全本**（按 Part 1–4，含 :688 的错误表和 :709 的教练哲学）→ FTT 网站正手系列文章（`ftt/04_ftt_blog_forehand_1/2.md`）→ YouTube 按「准备 → 前挥 → 触球 → 训练」主题依次过，而不是按发布时间或热度。每看完一期就入一张 SRC 卡，并更新 tree.md。树长全了，「看透一个体系」才真正落地。

## F. 风险与需要用户拍板的点（3 个）

1. **诊断时到底谁说了算。** 用户要求 FTT 做主干，但 CLAUDE.md 的引用排序是 Tennis Science > HSA > JUL > FTT，统一框架又把 USER 放第一（A5）。建议拍板：**诊断树以 FTT 为准，其他体系只作挂靠的辅证；用户自己的领悟一律先进问题登记表，作为假设，不再宣告「圣经」**。这需要用户同意，之后才能改 CLAUDE.md（本方案不改）。
2. **机位和设备。** 正侧面机位是整个方案能否提高可靠性的关键。需要确认：有没有第二部手机或三脚架；发球机场地的侧面是否能安全放机位（不被球打到）。只有一部手机也能做，就是两组轮换，速度慢一半。
3. **要不要花一次钱做「真人校准」。** 不校准的话，我们无法知道这套系统的诊断准不准，可能只是「更有条理地出错」。建议在第 3–4 周请一次真人教练，或者找远程视频点评（FTT 是否提供付费点评服务，我**不确定**，需要查），对同一段视频做对照。

**其他已知风险**（不需要拍板，但要知道）：
- 即使机位规范，手机 2D 视频对深度、旋转、拍面的判断仍有上限，C 层永远要靠体感和测试。
- 第 8 步把 FTT 视频变成 SRC 卡时，旧分析里有模型编的元数据，必须抽检，否则会把错误固化进树里。
- 树建好之后最大的诱惑，是又回到「多学概念」。按 Intuition-First，**用户场上只带一个外部目标**；这棵树是给我们诊断用的，不是给用户场上背的。
